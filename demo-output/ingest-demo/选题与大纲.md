## 主论点

> **支付超时率高的根因通常不是算得慢，而是同步依赖链太长——先砍依赖，再谈优化。**

四条标准检查：20 字内说得清 ✓；有 ≥2 条独立支撑 ✓；读者读完能决定顺序 ✓；与垂类一致 ✓。

被删掉的候选：

| 候选 | 为什么删 |
| --- | --- |
| 缓存和降级能解决超时 | 太宽，是常识不是论点；且素材里缓存只覆盖一个点 |
| 超时治理要三步走 | 素材没写执行顺序，硬写就是编 |

## 论点树大纲

```text
话题：支付超时治理
读者：电商后端负责人 / 大促前不知先改哪块 / 能定优化顺序
主论点：超时根因是同步依赖链太长，先砍依赖再谈优化
├─ 支撑 1：超时集中在晚高峰，是峰值放大，不是平均性能不够  ← [D5][F1]
│   ├─ 证据：68% 的超时请求集中在 20:00–22:00；原超时率 2.1%
│   └─ 读者动作：先看自己超时是否也集中在峰值段
├─ 支撑 2：见效最快的一刀是把同步调用改成异步  ← [D3]
│   ├─ 证据：风控调用同步改异步，平均耗时下降 180ms
│   └─ 边界：下游必须能接受最终一致，否则不能这么改  ← [O1]
├─ 支撑 3：缓存和降级是兜底，不是主力  ← [D4][F2]
│   ├─ 证据：缓存命中率 43%；降级覆盖 12 个场景
│   └─ 读者动作：把这两项排在「砍依赖」之后
└─ 结果：超时率 2.1% → 0.3%  ← [D1]
    └─ 限定：灰度 20% 流量，观察 14 天（不能写成「全量上线后」）
骨架：writing-playbook.md §4.2（问题—归因—解法）
```

**注意支撑 3 的写法**：缓存命中率 43% 单独看是「有效」的证据，但它支撑不了「先做缓存」。
这里只能支撑「缓存是兜底」这个次要判断——论据和论点必须对得上（§3.3）。

## 缺口清单

| 编号 | 优先级 | 缺口 | 影响 |
| --- | --- | --- | --- |
| G1 | P0 | 改造前的链路耗时基线（只有「下降 180ms」，没有原值） | 读者无法判断优化幅度，只能写「下降」不能写「降了 X%」 |
| G2 | P0 | 灰度 20% 是否已全量 | 决定结论能说「上线后」还是「灰度后」，措辞差一级 |
| G3 | P1 | 「行业常见 1%」的出处 | 没出处就不能写「高于行业水平」 |
| G4 | P1 | 缓存缓存的是什么（D4 缺上下文） | 读者无法复用这个动作 |
| G5 | P2 | 三个动作的实际顺序与工时 | 有则更好，无则用「优先级」表达而非「步骤」 |

**直接不写的一项**：`?1` 支付转化率（5.8% / 6.1% 口径冲突）。
不是降级处理，是这条数据本身不该进这篇——它的口径问题会污染主论点。
