# wechat-mp 第一批关键修复设计

## 已确认目标

用户已确认先修复评估中的关键问题：事实与授权保护、发布检查漏检、素材候选句丢失与同名来源覆盖。保持现有 CLI、四套主题与 L3 未实现边界，不扩展功能。工作目录不是 Git 仓库，不提交、不推送。

## 设计

### 事实保护契约

原作者观点必须保留身份与可核对出处；出处不明先补来源或排除，不改写成作者亲历。授权、许可或保密义务不明时暂停使用，脱敏、改量级不能解除义务。正文素材卡之外保留“许可与限制”记录：来源、署名要求、使用范围、免责声明中的论证限制、授权状态。精确值与近似值不互换。高风险人工复核采用待复核、确认误报、完成修订、拒绝发布四种状态；扫描通过不等于允许发布。

### 发布检查

保留 `build_report(md, title, summary, rules, html_path=None)` 原有调用参数，在末尾增加 `meta=None`。CLI 把 frontmatter 传入，覆盖后的 title/summary 是最终检查对象。元信息中的 title、title_short、summary 必须非空并分别满足规则集的 64、20、120 字限制；限制计数继续用 Python 字符长度，不在本轮声称核实现行微信限制。title、title_short、summary、cover_title、author、tag 逐字段独立扫描，不把元信息当代码而屏蔽；finding 的 field 标明来源，正文行号仍相对正文。超长、缺失或不支持的多行字段值产生 high finding。显式指定但不存在的 HTML 同样为 high。外域图片继续作为 medium 提示，不改变既有 CLI 约定。`--strict` 遇到 high 返回 1，不增加自动发布能力或误报豁免开关。

### 素材摄入

只按完整句子去重，保留数值、单位、时间范围及精度差异；候选句保留全文，避免后半句的数据被截掉。默认候选句不再截至 80 条；显式 limit 仍可用于直接函数调用。同名来源先沿用扩展名区分，再对所有输出基名做全局唯一分配，后缀递增，避开自然存在的后缀名；冲突键使用 NFC Unicode 规范化与 casefold，避免 macOS 上视觉相同的编码或大小写差异覆盖产物。在写任何文件前完成分配，JSON/汇总表继续指向实际产物。

## 验收与测试

使用 Python 标准库 unittest，无需安装依赖。先确认回归用例在旧实现失败，再修复并全量运行。覆盖必填、边界长度、标题摘要风险、CLI 覆盖、元信息反引号、正文代码屏蔽、JSON 和 strict 返回码；覆盖长句、相同句首不同数字、80 条以上素材、真实重复句、同名同格式及后缀碰撞。文档契约测试检查危险出口已被替换、许可信息必须保留、涉密内容不被改写放行。

不改已有 outputs/wechat-mp，不重跑需要 Pillow、Office 解析依赖或公众号权限的链路。新发现的 lint.py 是既有内容，本轮不改动。
