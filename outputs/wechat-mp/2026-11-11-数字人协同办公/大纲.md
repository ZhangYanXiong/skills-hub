## 主论点

> **数字人能不能进办公室，卡的从来不是技术，而是三件流程上的事：权限给到哪、决定谁签字、出错能不能撤回。**

四条标准检查：20 字内说得清 ✓；有 ≥2 条独立支撑（靠机制推理而非数据）✓；读者读完能产生判断 ✓；与垂类一致 ✓。

被删掉的候选：

| 候选 | 为什么删 |
| --- | --- |
| 数字人将取代一部分岗位 | 太宽，且无据可依，典型标题党 |
| 数字人的形象越像人越好 | 与办公场景的实际需求相悖，且没有反例素材 |
| 接入数字人要先做数据治理 | 正确但太泛，是另一个话题 |

## 论点树大纲

```text
话题：数字人协同办公
读者：正在评估数字员工的技术/产品负责人 / 试用过但落不了地 / 能判断现在能不能接
主论点：卡的不是技术，是权限、责任、可校验三件事
├─ 支撑 1：权限给到哪一层，决定它能干多少
│   ├─ 证据：能力分级（只读 / 可写 / 可代发）与风险同步上升
│   └─ 判断标准：做错了能不能 10 分钟内发现并撤回
├─ 支撑 2：它签字，还是你签字
│   ├─ 证据：直接对外 vs 人确认后发出，两种模式的失败后果不同
│   └─ 边界：制度没写清责任归属前，不要让它直接对外
└─ 支撑 3：产出必须能被快速判断对错
    ├─ 证据：有出处 / 有不确定性提示 / 结构化，三条缺一不可
    └─ 读者动作：只能「整体读一遍感觉一下」的场景，还不成熟
骨架：writing-playbook.md §4.4（观点论证式）
```

## 素材缺口清单

**这篇是「无素材」写作，所以缺口清单是空的——它不是遗漏，是必须如实告知的部分。**

| 编号 | 优先级 | 缺口 | 补上之后能升级成什么 |
| --- | --- | --- | --- |
| G1 | P0 | 一个真实落地场景（哪个环节、什么角色、节省了什么） | 从观点型升级为复盘型，说服力翻倍 |
| G2 | P0 | 数字人产品的能力边界（是否支持工具调用、系统集成、多轮任务） | 能写「哪些能做」，而不只是「该不该做」 |
| G3 | P1 | 企业内的权限审批链路（IT / 安全 / 法务谁批） | 能给出可执行的上线路径 |
| G4 | P1 | 一个失败案例 | 纠错型最有力的料，但也是最难拿的 |

**当前处理的降级方式**：`topic-expand.md` §5.3 的第二种——**缩小范围到「判断标准」**。
不写「怎么接」，只写「现在能不能接」。范围小了，但每一句都站得住。

明确不做的事：不编造任何百分比、不编造「某公司」「某团队」的实践、不虚构使用时长。
