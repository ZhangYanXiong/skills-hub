# 素材摄入与提炼（ingest）

> 用途：用户丢来一个 PDF / docx / PPT / 网页 / 长文，要改成公众号文章时，用这份文档把「原始素材」变成「可引用的素材卡」。
> 配套：`topic-expand.md`（素材卡 → 大纲）、`writing-playbook.md`（写作）、`compliance.md`（合规）。

---

## 0. 先分清：提炼 ≠ 摘要

这是最容易做错的一步。

| | 摘要 | 提炼（本文要的） |
| --- | --- | --- |
| 产出 | 「本文介绍了支付链路优化的背景、方法和结果」 | 「支付超时率从 2.1% 降到 0.3%，灰度 20% 流量，观察 14 天」 |
| 读者 | 想知道讲了什么的人 | 要写文章、需要能直接引用的人 |
| 判断标准 | 覆盖全面 | **每一条都能独立成立、可直接写进正文** |

摘要的句子拿进文章里全是废话（「本文介绍了…」），提炼的句子拿进来就能用。
**所以提炼的目标不是压缩，是抽出「可被引用的一句」。**

## 1. 第一步：机械提取（先用脚本，别直接读原文）

在仓库根目录执行，提取结果留在当前作品目录，不在根目录创建out：

```bash
python3 -I -B skills/wechat-mp/scripts/ingest.py 素材.pdf -o outputs/wechat-mp/my-article/ingest
```

```bash
python3 -I -B skills/wechat-mp/scripts/ingest.py 报告.docx 会议纪要.pptx 网页.html -o outputs/wechat-mp/my-article/ingest
```

支持格式：

| 格式 | 支持 | 说明 |
| --- | --- | --- |
| `.md` `.txt` | ✅ | 直接读 |
| `.html` `.htm` | ✅ | 去脚本/样式/导航/页脚 |
| `.docx` | ✅ | 段落 + 标题样式 + 表格 |
| `.pptx` | ✅ | 标题 + 正文 + 备注 |
| `.pdf` | ✅ | 需 pypdf（已 vendored 到 `scripts/vendor`） |
| 扫描版 PDF | ❌ | 图片型 PDF 没有文字层，需先 OCR，脚本会明确报错 |

产出三个文件，**用途不同，别混着看**：

| 文件 | 内容 | 什么时候用 |
| --- | --- | --- |
| `<name>.clean.txt` | 清洗后正文 | 回查原文、核对数字 |
| `<name>.outline.md` | 结构树 + 字数/段落统计 + 长文分块建议 | 判断素材有没有骨架、多长 |
| `<name>.facts.md` | 候选可引用句（带行号）+ 数值清单 + 同句多值提示 | **提炼的主战场** |

为什么必须先跑脚本：直接让模型读 PDF，会跳读、漏掉结论章节、把数字记错。脚本把「数字出现在第几行」固定下来，后面每条引用都能回查。

**多源素材**先看 `out/ingest/index.md` 的汇总表，再决定怎么合并（见 §6）。

## 2. 第二步：抽素材卡

### 2.1 四类卡

| 前缀 | 类型 | 判定标准 | 例子 |
| --- | --- | --- | --- |
| `F` | 事实 | 客观陈述，无需推断 | 本次改造影响 19 个接口 |
| `D` | 数据 | 含数字 + 单位 + 口径 | 单接口代码行数 42 → 11（口径：查询类接口） |
| `O` | 观点 | **原作者的主张**，不是客观事实 | 作者认为抽象的价值在于降低新增成本 |
| `?` | 存疑 | 矛盾、无出处、需要核实 | 转化率 5.8% 与 6.1% 口径不一致 |

**F 和 O 必须分开。** 把作者的个人判断写成「事实上」，是最常见的翻车方式——原文说「我推测」「我认为可能」，提炼时绝对不能变成陈述句。

### 2.2 卡片格式

用表格，编号在正文里以 `[F1]` `[D2]` 形式引用：

```markdown
| 编号 | 类型 | 内容 | 出处 | 备注 |
| --- | --- | --- | --- | --- |
| F1 | 事实 | 后台项目共 19 个接口，每个接口重复鉴权/日志/包装/兜底四段逻辑 | L3 | — |
| D1 | 数据 | 单个查询接口 42 行 → 11 行 | L12、表格1 | 改造前后对比 |
| D2 | 数据 | 支付超时率 2.1% → 0.3% | L21 | 灰度 20% 流量，观察 14 天 |
| O1 | 观点 | 作者认为抽象的代价是 Debug 路径变长 | L17 | 作者主张，非事实 |
| ?1 | 存疑 | 支付转化率 5.8% 与另一口径 6.1% 不一致 | L25、L29 | 需确认口径 |
```

**出处列写行号**，不要写「原文提到」。行号是回查的唯一抓手。

### 2.3 粒度标准

- **一张卡一件事**，超过两行就拆
- 能独立成立：单独发给不了解背景的人，他能看懂
- 带口径：数据卡必须写清时间、范围、样本，缺了就进 `?`
- 一条素材只能进一张卡，不要重复挂号

### 2.4 必须丢掉的东西

| 丢 | 原因 |
| --- | --- |
| 页眉页脚、页码、目录、致谢 | 无信息量 |
| 「本文将介绍…」「下面我们来看…」 | 元话语，是结构不是内容 |
| 与引用资格、结论范围无关的重复说明 | 先确认不影响许可、署名或论证限制，再从正文素材卡省略 |
| 重复表述 | 同一事实出现多次，只留最完整那条，其余记作出处 |
| 大段背景铺陈 | 除非它是论证前提，否则不占卡片位 |

**许可与限制必须保留**：免责声明、版权声明、使用条件不一概丢弃。单独保存 `许可与限制.md`，按来源记录署名要求、允许转载或修改的范围、免责声明中的结论适用边界、授权状态与待确认事项。正文素材卡可以省略无关说明，但原始材料与这份记录必须保留；脚本清洗正文不等于已经完成许可核对。授权不明先暂停使用，补授权或排除，脱敏或改量级不能替代授权。

**候选句完整性**：`ingest.py` 默认保留全部候选句及句子全文，只合并完整文本相同的重复句。相同句首、不同数字或口径仍分别保留；长文优先按结构分块查阅，不通过截掉候选证据来缩短输入。`facts.md` 只是检索辅助，数字仍须逐条回查原始材料。

## 3. 保真规则（红线，不可协商）

| 可以做 | 绝对不许做 |
| --- | --- |
| 合并同义句 | 改数字 |
| 调整语序、删冗余词 | 改单位（ms → 秒、万 → 个） |
| 把长句拆短 | 改时间范围（Q3 → 全年） |
| 换更通俗的说法（不改变含义） | 把「约 / 左右 / 接近」改成精确值或反之 |
| 标注原文出处 | 把「某渠道」扩写成「全量」 |
| — | 把推测（「可能」「预计」）写成事实 |
| — | 把两个来源的数据合并成一个「平均」 |

**精确值与近似值不互换**：原文「45 分钟」仍写「45 分钟」，不能擅自加「约」或写「接近一小时」；原文「约 45 分钟」保留「约」。如需换算，保留原始值与口径并明确注明换算过程，不把精确统计改成量级描述。

**不确定就问**：拿不准一个数字该不该用时，进 `?` 卡并在交付时列出，不要自己拍板。

## 4. 口径冲突处理

脚本能自动提示**同句相邻**的多值（「同一指标出现多个数值」）；
**跨句、跨来源**的冲突脚本关联不了，要看 `facts.md` 的「数值清单」逐行比对。

发现同一指标出现多个值时，按顺序问三个问题：

1. **同一时间点吗？** 3 月 5.8%、6 月 6.1%，不是冲突，是趋势
2. **同一统计口径吗？** 全渠道 5.8%、某渠道 6.1%，是范围差异
3. **同一定义吗？** 支付转化率可能把「点击支付」和「支付成功」都算进去

三种处理方式，选一种并写清楚：

| 情况 | 处理 |
| --- | --- |
| 确认是不同时间/渠道 | 两个都保留，正文里写清各自范围 |
| 无法确认 | 进 `?` 卡，**问用户**，不要猜 |
| 数据本身存疑 | 整条不用，换别的论据 |

**禁止：默默择一取用。** 数据错是发布后改不了的硬伤。

## 5. 素材缺口清单

抽完卡片，反过来检查「写这篇文章还差什么」。缺口四类：

| 缺口类型 | 表现 | 怎么补 |
| --- | --- | --- |
| 缺数据 | 有结论没有数字 | 问用户要指标，或改成定性表述 |
| 缺案例 | 有方法没有具体经过 | 问用户要一个真实场景（脱敏） |
| 缺对比 | 只有「改后」，没有「改前」 | 问改造前的基线值 |
| 缺出处 | 数字没有来源 | 标注「据 XX」，或删掉该数字 |

缺口清单直接写成**可照着问的话术**，不要含糊：

> 需要你补充三件事：
> 1. 改造前的基线是多少？（现在只有改造后 11 行）
> 2. 19 个接口是全量还是部分？
> 3. 「3 人天」是哪个团队估算的？

**没有缺口就当心**：素材太顺、什么都有，往往是二手总结稿，事实密度低，需要回问用户。

## 6. 多源素材合并

1. 每个源**单独**跑 `ingest.py`，产出各自的卡片
2. 先标来源：`F1（源 A）`、`F2（源 B）`
3. 合并规则：

| 情况 | 处理 |
| --- | --- |
| 多源一致 | 可信度提升，可标「多源一致」 |
| 多源不一致 | 全部进 `?` 卡，附各自出处 |
| 一手材料 vs 二手转述 | 以一手为准，二手只作补充 |
| 他人总结 vs 原始数据 | 以原始数据为准 |

源优先级：**原始数据 / 一手记录 > 官方文档 > 二手报道 > 他人总结**。

## 7. 和写作流程怎么接

```
素材文件
  ↓ ingest.py
clean.txt / outline.md / facts.md
  ↓ 本文 §2–§5
素材卡表格 + 缺口清单
  ↓ topic-expand.md §3
论点树（每个论点挂 [F1][D2] 编号）
  ↓ writing-playbook.md
正文
```

两个约定：

- 正文写作阶段**保留** `[F1]` 这类标记，方便回头核对
- 定稿交付时**去掉**标记，但在对话里说明「哪些数据来自哪份素材」

缺口的处理顺序：**先问用户 → 问不到就换角度 → 再不行才标注「待补充」**。
绝不能因为缺素材就编一个。

## 8. 完整示例

素材：一份「支付链路优化季度复盘」网页（273 字）。

**素材卡**：

```markdown
| 编号 | 类型 | 内容 | 出处 | 备注 |
| --- | --- | --- | --- | --- |
| D1 | 数据 | 支付超时率 2.1% → 0.3% | L21 | 灰度 20% 流量，观察 14 天 |
| D2 | 数据 | 订单列表 P99 从 1.8s → 420ms，日均 12 万次请求 | L23 | — |
| D3 | 数据 | 风控同步改异步，平均耗时下降 180ms | L13 | — |
| D4 | 数据 | 本地缓存命中率 43% | L15 | — |
| D5 | 数据 | 超时请求 68% 集中在 20:00–22:00 | L9 | 来源：支付中台统计 |
| ?1 | 存疑 | 支付转化率 5.8% 与另一口径 6.1% 不一致 | L25、L29 | 原文自述口径不一，需确认 |
| F1 | 事实 | 超时率原为 2.1%，高于行业常见 1% 水平 | L7 | — |
| F2 | 事实 | 降级覆盖 12 个场景 | L17 | — |

**缺口清单**：
1. 灰度 20% 是全量上线还是长期保持？（影响能不能说「上线后」）
2. 转化率口径以哪个为准？不一致就不要写转化率
3. 「行业常见 1%」的出处是什么？
```

注意 `?1` 和缺口清单里都提到了转化率——**这是同一件事的两面**：卡片负责记录，缺口负责追问。

## 9. 自检清单

提炼完，逐条过：

- [ ] 每条卡片都能独立成立，不需要上下文
- [ ] 数据卡都写了口径（时间 / 范围 / 样本）
- [ ] 出处列写的是**行号**，不是「原文提到」
- [ ] F（事实）和 O（观点）没有混
- [ ] 没有把「约」「可能」「某渠道」改写成确定表述
- [ ] 多值指标已进 `?` 卡，没有默默择一
- [ ] 缺口清单写成了可直接问用户的话术
- [ ] 删掉了页眉页脚、目录、元话语
- [ ] 同一事实没有重复挂号
- [ ] 所有数字都能在 `clean.txt` 的对应行找到原文
