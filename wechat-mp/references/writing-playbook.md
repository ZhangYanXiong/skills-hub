# 公众号写作 Playbook（技术/产品 · 职场/成长）

> 用途：AI agent 撰写公众号文章时的操作手册。所有示例只示范「结构」，其中的数字、公司名、项目名一律替换为真实信息，禁止照抄当成事实。
> 配套文档：`compliance.md`（发布前合规自查）、`layout-spec.md`（排版规范）、`SKILL.md`（整体工作流）。

---

## 0. 这份文档怎么用

**调用时机**：需要产出文章标题、摘要、开头、正文骨架、结尾，或对已有草稿做「去 AI 味」改写时。

**执行顺序**（不要跳步）：

1. 确认垂类：`技术/产品` 或 `职场/成长`。跨垂类时选一个主垂类，另一个只作为论据补充。
2. 确认读者：写清「他们是谁、当前卡在哪、读完后要能做什么」三件事，写不出来就停，先去确认。
3. 按 §2 出标题（长 + 短双版本），按 §6 出摘要，按 §4 选结构骨架。
4. 写正文，按 §3 打磨开头、按 §5 收尾。
5. 用 §7 过一遍 AI 味清单，用 §8 自检，再用 `compliance.md` 过合规。

**输出契约**：交付时至少包含 `标题（长）`、`短标题`、`摘要`、`正文 Markdown`、`自检结论` 五个字段，缺项视为未完成。

## 1. 两个垂类的语料基线

### 1.1 技术/产品

| 维度 | 说明 |
| --- | --- |
| 读者 | 一线工程师、技术负责人、产品经理、中小团队 CTO；时间碎、判断快、对空话零容忍 |
| 他们要的 | 可复现的结论、边界条件、代价与坑、代码/配置片段、选型依据 |
| 不要写的 | 只讲「是什么」不讲「什么时候会坏」；堆概念不落实例；用「赋能」「闭环」代替具体动作 |
| 可信度来源 | 真实数据（QPS、耗时、P99、成本、人力）、线上事故、可验证的复现步骤、明确标注的适用版本 |

**高频选题**：线上故障复盘、性能优化、技术选型对比、架构演进、代码评审、需求拆解、AI 能力接入的工程化落地、团队工程效率。

### 1.2 职场/成长

| 维度 | 说明 |
| --- | --- |
| 读者 | 工作 0–10 年的执行者与准管理者；关心晋升、汇报、协作、跳槽、心态 |
| 他们要的 | 具体场景里的具体动作、可直接套用的话术/模板、可对照的失败案例 |
| 不要写的 | 成功学口号、无法验证的「我在大厂学到的 3 件事」式空转、劝人「格局大一点」 |
| 可信度来源 | 真实经历（脱敏）、明确的时间线、得到的反馈、做错后的修正、可观察的结果 |

**高频选题**：周报与汇报、向上管理、跨部门协作、绩效面谈、晋升答辩、带新人、职业转型、时间与精力管理。

### 1.3 素材底线

- 涉及具体公司、同事、客户：先确认使用权限与保密义务，再去掉可识别信息；脱敏、改量级不能替代授权，也不能解除保密义务。
- 涉及业务数据：只用使用权限已确认的数据，公开可访问不代表可以任意转载或改写。授权不明：暂停使用，补授权或排除；精度、单位、时间范围与原始口径保持一致，不改成量级来绕过限制。
- 涉及他人观点、论文、开源文档：保留原作者身份与可核对出处。出处不明：补来源或排除，不把外部信息改写成自己的观察、亲历或原创判断。
- 许可与限制：记录来源、署名要求、允许使用或修改的范围、免责声明中的适用边界及授权状态。授权不允许修改时，不为了标题效果或合规话术擅自改写。

## 2. 标题：先过硬约束，再套公式

### 2.1 三条硬约束（必须写对）

| 项目 | 限制 | 后果 |
| --- | --- | --- |
| 标题 | 后台标题栏最多 **64 字** | 超出无法保存；从别处粘贴时会被截断，必须人工核对 |
| 摘要 | 最多 **120 字** | 超出无法保存；常见失败是写作时按 150 字写完再删 |
| 列表页展示 | 订阅号消息列表、聊天列表中的标题单行显示，**约 20 字后省略号截断** | 超过 20 字的核心信息在信息流里等于不存在 |

补充：列表页可见字数随机型、字号、系统版本浮动（约 18–22 字），分享卡片可显示更多但仍有截断。以上均为平台 UI 行为，随版本变化，**实际可见字数以后台和手机端显示为准（需人工核实），发布前核一遍**。

### 2.2 双版本标题工作法

后台只有一个标题字段，所以做法是：**一个长标题 + 一个短标题变体**。

- **长标题**（≤64 字）：完整信息 + 利益点 + 限定条件，用于分享卡片、搜索、历史消息页。
- **短标题**（≤20 字）：从长标题里抽出最锋利的那句，用于封面图文字、社群/朋友圈转发文案、视频号口播。
- **硬要求**：把「读者凭什么点」的决定性信息放在前 20 字内，后 20–64 字只做补充，不承载核心信息。

示例：

| 长标题（≤64 字） | 短标题（≤20 字） |
| --- | --- |
| 我们把 CI 构建从 18 分钟压到 4 分钟：三处缓存改动和一次踩坑复盘 | CI 从 18 分钟压到 4 分钟 |
| 第一次做技术负责人，最容易踩的 7 个坑（附沟通话术） | 新晋技术负责人的 7 个坑 |
| 绩效季前必看：把你的工作说清楚的 4 个汇报结构 | 汇报说不清？用这 4 个结构 |
| 30 岁后端的转型窗口：哪些能力迁移得动，哪些带不走 | 30 岁后端，什么能力带得走 |

### 2.3 十种可复用标题公式

每种公式先给「模板」，再给两个不同垂类的示例。示例里的数字是占位示范，按真实情况替换。

**① 数字型**：`【具体动作】+【数字结果】，我做了【数字】件事`
- 技术/产品：`一条 SQL 改写，让报表接口 P99 从 2.1s 降到 180ms`
- 职场/成长：`工作 5 年，我筛出 12 条周报写作原则`
- 关键：数字要可解释，别用「100 倍提升」这种无法验证的倍数。

**② 对比型**：`同样是【A】，为什么【B1】和【B2】差这么多`
- 技术/产品：`同样是 Java 转 Go，为什么有人三个月就能写生产代码`
- 职场/成长：`校招进大厂 vs 早期创业公司，三年后的差距在哪`
- 关键：对比双方要真实可辨，不能自己造一个假想敌。

**③ 身份代入型**：`给【具体身份】的你：【N】个【具体问题】`
- 技术/产品：`给第一次做技术面试官的你：别问这 6 类问题`
- 职场/成长：`写给 28 岁还在犹豫要不要转管理的你`
- 关键：身份要具体到「岗位 + 阶段」，越具体越有点击力。

**④ 反常识型**：`【公认做法】可能错了：我的【N】次翻车经历`
- 技术/产品：`不要过早抽象：我见过的过度设计都是这么来的`
- 职场/成长：`埋头努力没换来晋升：问题不在努力本身`
- 关键：反驳要给出替代方案，否则只是抬杠。

**⑤ 痛点型**：`【具体场景】时，别只会【最常见的错误动作】`
- 技术/产品：`线上 CPU 飙到 100%，别只会 top 和 jstack`
- 职场/成长：`每次评审都被问『这个需求价值是什么』，这样答`
- 关键：场景必须是读者每周都会遇到的真实瞬间。

**⑥ 结果承诺型**：`读完这篇，你能【可验证的具体能力】`
- 技术/产品：`读完这篇，你能独立设计一个限流方案`
- 职场/成长：`读完这篇，你能在 20 分钟内写完一份能交差的季度复盘`
- 关键：承诺必须由正文兑现；做不到就是标题党，直接损坏账号。

**⑦ 提问型**：`为什么你的【产出】总是【负面结果】？`
- 技术/产品：`为什么你的技术方案总被 challenge？`
- 职场/成长：`为什么你越努力，年终评价越普通？`
- 关键：问题要指向读者自己能改的部分，不要引向抱怨外部。

**⑧ 清单型**：`【垂类关键词】清单：【N】条【可执行标准】`
- 技术/产品：`Code Review 清单：10 条上线前必查项`
- 职场/成长：`述职材料清单：汇报前必过的 8 个自检项`
- 关键：清单条数要和正文条数一致，读者会数。

**⑨ 悬念/故事型**：`【时间/场景】+【反常事件】+【未交代的后果】`
- 技术/产品：`上线前一夜，我们把数据库回滚了`
- 职场/成长：`我拒绝了一次升职，一年后结果出乎意料`
- 关键：正文必须在首屏交代真实结果，不能整篇吊着不给。

**⑩ 时间/阶段型**：`【时间跨度】后回看：【当初的决定】对不对`
- 技术/产品：`微服务拆分两年后回看：哪些边界画错了`
- 职场/成长：`转岗一年后回看：当时该不该走`
- 关键：必须真的有时间跨度，不能把三个月写成「多年」。

### 2.4 标题自检（8 条，全部通过才算可用）

1. 前 20 字里有没有「读者凭什么点」的信息？
2. 字数 ≤64，且短标题 ≤20？
3. 有没有出现 `compliance.md` 里的极限词或承诺性表述？
4. 数字和结论在正文里找得到出处？
5. 去掉形容词后还剩下什么具体信息？
6. 是否出现了「震惊」「必看」「史上最强」这类透支信任的词？
7. 目标读者能否一眼看出「这是写给我的」？
8. 同一账号最近 10 篇里，是否重复用了同一种公式？（避免读者审美疲劳）

## 3. 开头钩子：前 3 行决定读者走不走

公众号正文首屏只有约 3 行可见。开头只做一件事：**让读者确认「这篇和我有关」**。

**① 场景共鸣**：还原一个读者熟悉的瞬间，不评价、不铺垫。
> 凌晨两点，告警群弹出一条消息：订单服务 P99 超过 3 秒。值班的是刚转正三个月的同事，他做的第一件事是去翻昨天的发布记录。
> 季度述职前一天，你把 PPT 改了 7 遍，还是不知道第一页该写「我做了什么」还是「业务结果是什么」。

**② 结论前置**：第一句就给结论，后面全是证据。
> 先说结论：限流方案里最容易被忽略的不是阈值，而是「被限流之后的返回值」。这篇文章讲怎么定这个返回值。

**③ 反直觉提问**：先抛一个和常识冲突的判断，再给理由。
> 性能优化最有效的动作，往往不是加缓存，而是删掉一次没必要的数据查询。这话听起来反直觉，但我们在三个接口上验证过。

**④ 数据冲击**：用一个具体、可解释、有出处的数字开场。
> 上一个季度，我们团队 46% 的线上问题来自配置变更，而不是代码。这个比例让我们把发布流程整个重做了一遍。
> 我统计了自己过去一年的 48 份周报，被领导直接退回重写的有 17 份，退回原因高度集中在同一处。

**⑤ 故事切入**：从一个人、一个决定、一个冲突点开始。
> 那天评审会上，产品经理问了一个问题：「这个功能上线后，你打算怎么判断它有用？」会议室安静了五秒。

**⑥ 痛点直指**：直接把读者的困境说出来，不寒暄。
> 如果你写的周报每周都被领导打回重写，问题大概率不在文笔，而在你写的是「我做了什么」而不是「结果是什么」。
> 线上 CPU 打满时，很多人的第一反应是扩容。但扩容只能买到 10 分钟，买不到根因。

**开头反面清单**（出现即删）：
- 「大家好，我是 XX，今天想和大家聊聊……」
- 「在当今这个 XXX 的时代，……」
- 「随着 XXX 的快速发展，……」
- 「首先，我们需要明确什么是 XXX」
- 开头先放整段免责声明、目录、作者履历。

## 4. 正文结构模板（5 套）

写作前先选骨架，再填内容。下表里的百分比指**正文字数占比**，按目标字数换算成具体段数。

### 4.1 干货清单式（最稳，技术/产品首选）

| 段落 | 意图 | 占比 |
| --- | --- | --- |
| 钩子 | 交代「为什么现在写这个清单」 | 10% |
| 使用前提 | 适用场景、版本、前置条件（不写会被骂） | 10% |
| 逐条展开（N 条） | 每条：一句结论 → 原理/原因 → 代码或例子 → 边界与反例 | 70% |
| 收束 | 行动清单 + 最容易失败的一条 | 10% |

**示例大纲**（《Code Review 清单：10 条上线前必查项》，2500 字）：钩子 250 字 → 前提 250 字 → 10 条 × 175 字 → 收束 250 字。
**常见失败**：每条长度不一、后几条只剩一句口号；没有「什么时候不适用」。

### 4.2 问题—归因—解法（故障复盘/排障首选）

| 段落 | 意图 | 占比 |
| --- | --- | --- |
| 现象 | 时间、影响面、用户可感知的表现 | 15% |
| 定位过程 | 排除路径、关键证据（日志、指标、抓包） | 25% |
| 根因 | 一句话根因 + 为什么之前没人发现 | 20% |
| 解法 | 改动、验证方式、回滚预案 | 20% |
| 预防 | 流程/监控/评审上的动作，最后一句回扣可复用结论 | 20% |

**示例大纲**（《一次 P0 复盘：连接池耗尽的 47 分钟》）：现象 600 字 → 定位 1000 字 → 根因 800 字 → 解法 800 字 → 预防 800 字。
**常见失败**：定位过程写成流水账，「我们查了很多地方」；根因只写表象（「连接泄漏」）不写代码层面的原因。

### 4.3 复盘叙事式（职场/成长首选）

| 段落 | 意图 | 占比 |
| --- | --- | --- |
| 背景与目标 | 当时的位置、约束、想要什么 | 10% |
| 关键节点（3–4 个） | 每个节点包含：冲突 → 我的判断 → 动作 → 结果 | 45% |
| 结果 | 用可核对的事实收口，不夸大 | 15% |
| 提炼 | 抽成 2–4 条可迁移的方法 | 20% |
| 留给读者 | 一个可自测的问题或一个可直接用的动作 | 10% |

**示例大纲**（《我拒绝了一次升职，一年后结果出乎意料》）：背景 250 字 → 4 个节点 × 280 字 → 结果 375 字 → 提炼 500 字 → 收尾 250 字。
**常见失败**：节点只有情绪没有决策；结果写得像爽文；提炼部分变成「所以人要努力」。

### 4.4 观点论证式（产品判断/职场观点首选）

| 段落 | 意图 | 占比 |
| --- | --- | --- |
| 靶子 | 把要反驳的常见说法完整、公平地讲一遍 | 10% |
| 主张 | 我的判断，一句话说清 | 10% |
| 论据 1/2/3 | 每条一个独立论据：案例、数据、机制 | 各 20% |
| 反方与边界 | 什么情况下我的观点不成立 | 15% |
| 结论 | 回到读者能做的事 | 5% |

**示例大纲**（《不要过早抽象》）：靶子 300 字 → 主张 300 字 → 三个论据各 600 字 → 边界 450 字 → 结论 150 字（总 3000 字）。
**常见失败**：把靶子写成稻草人；没有反方段落，读者不信。

### 4.5 教程实操式（工具/流程类首选）

| 段落 | 意图 | 占比 |
| --- | --- | --- |
| 成果预览 | 先给最终效果/截图，建立预期 | 10% |
| 环境与前置 | 版本、依赖、耗时、风险提示 | 10% |
| 步骤 1..N | 每步：目的 → 操作 → 验证 → 出错怎么办 | 65% |
| 验证与回滚 | 怎么确认成功、怎么撤销 | 10% |
| 边界 | 不适用的场景、已知限制 | 5% |

**示例大纲**（《用 GitHub Actions 搭一条 5 分钟上线的流水线》）：预览 400 字 → 前置 400 字 → 6 步 × 430 字 → 验证 400 字 → 边界 200 字。
**常见失败**：步骤缺验证方法；代码不写版本号导致读者跑不通。

## 5. 结尾与转化：三条不违规的路径

**① 提问式收尾**：把评论区变成延伸讨论，不索取行为。
> 你们团队的发布流程是怎么卡住配置变更的？评论区说说，我会挑几个典型场景整理成下一篇。

**② 系列预告 + 关注理由**：给出「关注能持续得到什么」，不提任何奖励。
> 这是「线上故障复盘」系列的第 3 篇，前面讲过连接池和缓存击穿，下一篇讲限流返回值的设计。关注这个系列，新的复盘会继续更新。
> 这是「汇报与晋升」系列的第 4 篇，前三篇分别讲目标对齐、过程留痕和答辩表达，下一篇讲怎么准备绩效面谈。关注这个系列，新的拆解会继续更新。

**③ 价值总结 + 作者动作**：用一句可带走的结论收尾，落款说明作者背景与联系方式（公开信息）。
> 一句话总结：优化的第一步是先证明「这里有浪费」，而不是先想「加什么」。后续我会把这次用到的指标看板配置整理出来。

**明确禁止**（属于诱导关注/分享/点赞，见 `compliance.md`）：
- 「转发到朋友圈截图后台领取资料」
- 「集满 N 个赞解锁下一篇」
- 「点赞 + 在看，抽 3 位送书」
- 「关注后回复关键词领取完整版」
- 「不转发就看不到后续」

允许的替代做法：把资料直接放在正文（或正文可访问的站内文章里），在结尾说明「资料在文末，可直接取用」。

## 6. 摘要写法（≤120 字）

摘要在未填时，微信会截取正文前 54 字自动生成（版本间可能不同，以实际显示为准），因此**建议始终手写**。三种风格：

**① 结论式**：把全文最硬的结论压进去。
> 线上问题里近一半来自配置变更，不是代码。这篇拆开我们重做的发布流程：变更分级、灰度顺序、回滚指标，以及为什么「能回滚」比「能灰度」更重要。（69 字）

**② 悬念式**：给冲突，但承诺正文会回答。
> 评审会上，产品经理问「这个功能上线后你打算怎么判断它有用」，会议室安静了五秒。这篇讲需求评审里最该先回答的那个问题。（58 字）

**③ 清单预览式**：直接列要点，适合干货类。
> 一条 SQL 把报表接口从 2.1s 压到 180ms 的三步：去掉隐式类型转换、拆开 OR 条件、补上组合索引。附执行计划对比与适用边界。（70 字）

**硬要求**：≤120 字；不重复标题原文；不出现极限词；写完后按字符数数一遍（中英文、标点都计入）。

## 7. 「AI 味」负向清单

读者对机器腔的容忍度极低。下表左边出现一次就要处理，出现两次以上读者会弃读。

| 典型表达 | 问题 | 替换建议 |
| --- | --- | --- |
| 在当今数字化/信息化时代 | 零信息开场 | 直接写一个具体场景或时间点 |
| 随着 XX 的快速发展 | 同上，且是万能填充 | 写「XX 从 A 变成 B」的具体变化 |
| 综上所述 / 总而言之 | 读者已经知道要收尾了 | 直接给结论，或用「所以」 |
| 首先、其次、最后（连续三段） | 机械结构暴露生成痕迹 | 用带信息的小标题，或直接并列陈述 |
| 值得注意的是 / 需要指出的是 | 空转提示语 | 删掉，内容自己会说话 |
| 不难发现 / 众所周知 / 毋庸置疑 | 替读者做判断 | 把判断写成事实或删掉 |
| 让我们一起…… / 接下来我们来看 | 填充过渡 | 删掉，直接进入内容 |
| 极大地提升了效率 | 无数字的形容词 | 给数字：耗时、成本、人力变化 |
| 赋能 / 抓手 / 闭环 / 颗粒度 / 底层逻辑 | 黑话替代具体动作 | 写具体动词：接入、复用、对齐、拆分 |
| 不仅……而且…… 连续使用 | 句式单一 | 拆成两句，各说一件事 |
| 作为一名 XX 工程师 | 自我标签化开场 | 直接讲事和判断 |
| 这个问题的答案可能和你想的不一样 | 空悬念 | 直接把不一样的答案说出来 |
| 这是一个非常好的问题 | 客套 | 删 |
| 我们可以看到 / 可以看出 | 冗余引导 | 直接给观察结果 |
| 建议大家一定要重视 | 无落点的建议 | 给一个今天就能做的动作 |
| 希望这篇文章对你有帮助 | 万能收尾 | 换成一句可带走的结论或下一步 |
| 每段都以「其实」/「那么」开头 | 语感机械 | 变换开头，或直接陈述 |
| 三个反问句连用 | 显摆节奏 | 只留最关键的一个反问 |
| 每句话都加粗 / 满屏 emoji | 视觉噪音，遮掩内容空洞 | 每节最多一个加粗重点 |
| 排比三连（更高、更快、更强） | 空洞修辞 | 换成具体事实 |
| 大量使用「我们认为」却不给依据 | 权威感伪装 | 给数据、案例或明确标注为个人判断 |
| 「深入探讨」「全方位解析」 | 空承诺 | 写明到底讲哪几点 |
| 中英混杂且无必要（「这个 feature 的 value」） | 影响阅读 | 首次出现给中文+英文，之后只用一种 |
| 「很多人问我……」 | 常见模板腔 | 直接说要讲的问题 |

**自查方法**：把文章通读一遍，凡是「删掉后信息量不变」的句子，全部删掉。AI 味的本质是**信息密度低**，不是用词问题。
